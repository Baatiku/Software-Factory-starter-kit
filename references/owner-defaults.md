# Reusable engineering preferences (public, non-sensitive)

These describe general working standards, not private profile information or binding architecture. The project owner's direct requirements and actual context always take priority.

- Make safe, reversible product and engineering choices independently; consolidate only high-impact ambiguities into one decision review.
- Prefer compact, familiar, low-friction UI, sensible defaults, excellent mobile responsiveness and useful inline actions. Simplicity over feature proliferation.
- Plan all screens and journeys up front—including errors, edge cases, admins and recovery—to reduce back-and-forth and costly rework.
- Research established competitors, small challengers and substitutes; borrow proven patterns ethically; explicitly avoid needless features and seek genuine value gaps.
- Choose reliable, maintained, best-value stacks and providers after dated comparisons and three-scale TCO analysis. Avoid expensive fixed commitments, unnecessary SaaS subscriptions and lock-in without reason.
- Prefer working end-to-end source, real devices/providers/integrations, truthful evidence and stable production operations over disconnected mock screens.
- Parallel ChatGPT/Codex windows work only on independent claimed files; central integration and verification have protected ownership.
- For weak connectivity or constrained devices, prioritize low-data, retry, offline-safe experiences when applicable.
- No developer API tokens or infrastructure secrets shown to ordinary end users.
- Treat languages, payment rails, hosting, visuals, brand, platform, voice and feature lists as *per-product* choices, not universal defaults.
- Protect confidentiality: this public kit does not contain personal account details, private past-chat content or secret project configurations.

To customize: copy into a **private** owner-specific file or local ChatGPT Custom Instructions; do not commit personal secrets or sensitive history.
