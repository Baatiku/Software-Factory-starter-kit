# Continuous improvement loop and change control

Every defect, rework incident, integration collision, price surprise, missing screen, or support escalation yields a short lesson entry: date, what failed, impact/time lost, root cause, detectability, proposed durable rule, owner, validation test and change link.

Classify as global enduring preference / factory-wide reusable method / project-specific requirement / obsolete decision. Only factory-wide lessons modify this repo. Avoid importing a product-specific solution as a default.

Changes require an issue or rationale, minimal focused PR, documentation/spec diff, regression test where mechanizable, changelog entry and compatibility analysis. Use semver-ish kit releases; breaking scaffold/template changes require migration notes. Prefer small quality gains over accumulating additional checklist bureaucracy.

Schedule optional periodic audits of stale vendor pricing, standards, broken links, security guidance, template quality, outdated assumptions and actual adoption metrics. Do not promise continuous background monitoring unless an explicit scheduled automation/service is installed.

Measure: missed requirements, late screen redesigns, overlapping paths, PR verification time, test escape rate, provider-cost variance, cost per active user, restore drill results and post-release defects. Retire rules and features that fail to improve outcomes.

This repository is a living artifact: GitHub remains authoritative, not chat memory alone. A new chat reads this repo to retrieve the current rules.
